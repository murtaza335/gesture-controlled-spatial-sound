Gesture-Controlled Spatial Audio Mixer

A browser application that tracks both hands through a webcam, places sounds around the listener's head in headphones, shapes their tone with gestures, and shows the sound as a live visual.

Full title
Gesture-Controlled Spatial Audio Mixer with Real-Time Visualization and Binaural Rendering

01Overview

Problem statement

Most audio interfaces rely on small buttons, knobs and sliders, and they present sound as flat left/right stereo. That is a barrier for people who cannot see a screen or cannot operate small controls, and it hides the spatial nature of sound from everyone else.

This project builds a touchless interface in which the user's hands become the controls. The right hand moves a sound source around the listener's head using binaural (HRTF) rendering, so it is heard as coming from a direction. The left hand shapes the sound: bass, treble, pitch, filter and reverb. A live waveform, spectrum and 3D view show what is happening.

How position becomes sound. The sound source (blue dot) sits at an azimuth angle around the head. Moving the right hand left or right sweeps it around this ring; hand height sets elevation; how close the hand is to the camera sets distance (inner vs. outer ring). Left/right is the most reliable axis to hear, so the demo is built around it.

Primary use case

Accessibility. Spatial-audio games and navigation for blind and visually impaired users, where sounds are placed and found in space by gesture. This matches the course's focus on intelligent interfaces for impaired users and gives a clear target group for the user study. Music mixing (placing instruments in 3D and shaping their tone by hand) is the secondary demo.

02Objectives

  • Track both hands in real time from a standard laptop webcam, entirely in the browser.
  • Map hand position to a 3D sound position (azimuth, elevation, distance) and render it binaurally for headphones.
  • Control tone (bass / mid / treble, pitch, filter, reverb, volume) with a separate set of left-hand gestures.
  • Visualize the audio as a waveform, a frequency spectrum and a 3D scene that links the visual to the sound's position.
  • Offer an accessibility mode that can be used without looking at the screen.
  • Evaluate the interface with real users: usability (SUS), gesture vs. slider performance, and sound-localization accuracy.

03Scope

Core (MVP)

  • Webcam hand tracking in the browser
  • One sound source moved by the right hand
  • HRTF binaural rendering in headphones
  • Pinch to grab / release the source
  • Simple 2D view of hand and source
  • Smoothing of tracking jitter

Extended (planned)

  • Left-hand tone controls (EQ, pitch, filter, reverb)
  • Waveform + spectrum visualizer
  • 3D scene in Three.js
  • Multiple sound sources / instrument stems
  • Swipe to change track
  • On-screen gesture labels and help

Stretch (pick one)

  • Head tracking so sounds stay fixed in the room
  • Accessibility game: find and catch sounds by ear
  • True pitch-only shifting

Out of scope

  • Mobile / tablet support
  • Multi-user or networked sessions
  • Personalized (measured) HRTFs
  • Depth cameras or extra hardware
  • Real-world indoor navigation

Head tracking, multi-user and mobile support each add several days. They are added only once the core works.

07Approach & architecture

The two hard problems, hand tracking and HRTF rendering, are already solved by mature libraries. The work is connecting them, designing the mapping from gestures to sound, and making the interface feel good. Everything runs client-side in one browser tab to keep latency low.

Processing pipeline (every video frame)

1

Capture

Webcam frames via getUserMedia, mirrored so movement feels natural.

2

Hand tracking

MediaPipe Hand Landmarker returns 21 3D landmarks and handedness for each hand.

3

Smoothing

A One Euro filter on each landmark removes jitter while staying responsive to fast moves. Depth comes from hand size (wrist to middle-finger base distance).

4

Gesture recognition

Rule-based detectors (pinch distance, finger states, swipe velocity, tilt and twist angles) with hysteresis and debouncing to avoid accidental triggers.

5

Mapping

Normalized hand values are mapped to audio parameters with calibrated ranges and response curves (e.g. logarithmic for frequency and volume).

6

Audio engine

The Web Audio graph is updated with smooth parameter ramps and rendered binaurally to the headphones.

7

Visualization

An analyser tap feeds the waveform, spectrum and 3D scene, drawn on each animation frame.

Audio graph (per sound source)

AudioBufferSource / MediaElementSource
  → BiquadFilter (lowshelf, bass)
  → BiquadFilter (peaking, mid)
  → BiquadFilter (highshelf, treble)
  → BiquadFilter (lowpass, filter sweep)
  → split ─┬─ dry ───────────────┐
           └─ Convolver (reverb) ┴→ Gain (volume)
  → Panner (panningModel = "HRTF", distanceModel = "inverse")
  → master Gain → AnalyserNode → destination (headphones)

AudioListener ← head-tracking yaw (stretch goal)

Coordinate mapping

Hand input (normalized)Sound parameterRange
x: 0 (left) → 1 (right)Azimuth−90° → +90° (front half; ±180° with an "orbit" mode)
y: 0 (bottom) → 1 (top)Elevation−30° → +45°
Hand size: small → largeDistance5 m → 0.5 m

Spherical values are converted to the panner's x / y / z position each frame. The 3D view uses the same coordinates, so what the user sees matches what they hear.

Why the browser and JavaScript. Python with OpenCV would also work, but it would need a separate audio engine and a bridge to the UI, which adds latency and setup. In the browser, tracking, audio and visuals share one event loop and the app runs from a link with no install.

Working with Claude

Claude will be used to write and debug the MediaPipe, Web Audio and Three.js code, design the gesture mapping, and draft the study questionnaire and report. The team is responsible for everything that needs ears, eyes and hands: testing with headphones and a camera, tuning smoothing, sensitivity and range by feel, and running the user study with real participants.

10Evaluation plan

The study targets 8–12 participants, including visually impaired users if they can be recruited, otherwise sighted users who are blindfolded for the accessibility tasks.

StudyMethodMeasures
Gesture vs. slidersWithin-subjects: each user completes the same tasks (e.g. "place the drums to your left and boost the bass") with gestures and with the slider panel, in counterbalanced orderTask completion time, accuracy, errors
UsabilitySystem Usability Scale questionnaire after each condition, plus short interviewsSUS score (0–100), qualitative feedback
Sound localizationA sound plays at a hidden position; the user points where they hear it. HRTF vs. stereo-pan conditionsAngular error (°), front/back confusion rate
Gesture learnabilityUsers try each gesture after a short demoSuccess rate on first try, accidental triggers per minute
